# Tracefold

Відкритий інструмент для дослідження руху коштів між блокчейн-адресами.

> **Стан проєкту: ранній прототип.** Огляд читає збережені адреси, синхронізовану історію та зв’язки вибраного розслідування через локальний API; це не глобальний індекс гаманців. Баланси в мережі не відображаються, автоматичні мітки сутностей не призначаються. Таблиця транзакцій порожня, доки історію не синхронізовано з налаштованим джерелом. Панель ризику завантажує сигнали аналітика для вибраної адреси й може врахувати точний збіг OFAC SDN після явної перевірки локального знімка; версія оцінки попередня й не є юридичним висновком або повною комплаєнс-перевіркою. Compose `sync-worker` періодично оновлює відстежувані адреси через налаштовані адаптери з цільовим інтервалом п’ять хвилин за достатньої потужності провайдера; це обмежене опитування історії, а не моніторинг у реальному часі чи всього mempool. Граф поєднує збережені події відправника й отримувача з EVM, TRON, Solana, XRPL, TON та Aptos і досліджує шляхи до трьох переходів. Cardano і Sui показують ненаправлені зв’язки учасників однієї транзакції; вони не вважаються прямими переказами й не використовуються для пошуку шляхів. Зв’язок Sui потребує повного набору з двох рівних і протилежних змін балансу одного типу монети. Кожен перехід — окреме спостереження; шлях не доводить, що ті самі кошти пройшли весь маршрут. Контрагентів Bitcoin не виводимо. Каталог містить Ethereum, Base, Arbitrum One та інші EVM-мережі; доступність історії залежить від провайдера і його налаштувань. Перевірка точної адреси за локально імпортованим знімком OFAC SDN доступна для Bitcoin, Ethereum, TRON та XRP Ledger. Повнота й строк зберігання відрізняються між мережами; попередній скоринг не є комплаєнс-рішенням.

**Документація:** [Русский](README.ru.md) · [Українська](README.uk.md) · [English](README.md)

Граф розслідування використовує збережені зв’язки відправника й отримувача з EVM, TRON, Solana, XRPL, TON та Aptos. Cardano і Sui показують ненаправлені зв’язки учасників однієї транзакції; вони не вважаються прямими переказами й не використовуються для пошуку шляхів. Для Sui зв’язок потребує повного набору з двох рівних і протилежних змін балансу одного типу монети. Знімок фіксує граф разом з ID вихідних спостережень і відкривається повторно. Обмеження описані в [документації API знімків](docs/uk/graph-snapshots-api.md).

## Про проєкт

Tracefold задуманий як OSINT-інструмент для розслідувань. Аналітик зможе почати з адреси, простежити перекази в підтримуваних мережах, зберегти підстави кожного зв’язку та перевірити сигнали ризику. Алгоритмічну оцінку не слід сприймати як доказ.

Інтерфейс показує огляд на основі даних вибраного розслідування з API, граф мультичейн-зв’язків зі збереженням знімків, фільтри мереж, таблицю спостережень і пояснювану версійну оцінку вибраного гаманця. Мітки гаманців задає аналітик; відображення балансу та автоматична атрибуція сутностей не реалізовані.

## Принципи

- Для кожної знахідки показувати мережу, адресу, посилання на транзакцію, джерело і час спостереження.
- Відокремлювати спостережувані транзакції від користувацьких міток і гіпотез аналітика.
- Показувати мережу як припущення, яке треба підтвердити: адресу формату EVM можна використовувати в Ethereum, Base, Arbitrum та інших сумісних мережах.
- Називати оцінку індексом ризикової експозиції, а не ймовірністю чи доказом порушення.
- Показувати повноту покриття й актуальність даних; не створювати враження, що відстежуються всі гаманці та мережі.

## Розслідування

Створіть або відкрийте розслідування в розділі **Investigations**. У кожному розслідуванні окремо зберігаються адреси, історія та знімки графа. Вибране розслідування запам’ятовується в цьому браузері; якщо його більше немає на сервері, вибирається перше доступне. Адреса з огляду додається до активного розслідування. Якщо розслідувань ще немає, API створює розслідування за замовчуванням під час першого збереження адреси. Перемикання змінює список адрес, стрічку подій, граф і знімки. Дані різних розслідувань не об’єднуються. API поки не має автентифікації та контролю доступу користувачів.

## Поточний стек

- **Frontend:** React, TypeScript, Vite та Tailwind CSS.
- **API:** локальний сервіс на Rust і Axum.
- **Постійні дані:** PostgreSQL; початкова міграція створює таблиці розслідувань, відстежуваних адрес і сигналів ризику.
- **Черга й координація:** Redis Streams для фонового worker-а; API також перевіряє доступність Redis у readiness endpoint.

API підтримує створення й перегляд розслідувань та відстежуваних адрес, ручну синхронізацію історії підтримуваних мереж через налаштовані адаптери провайдерів, сигнали ризику від аналітика й перевірку точної адреси за імпортованим знімком OFAC SDN. Таблиця останніх транзакцій показує збережені спостереження та їхнє джерело. Панель ризику завантажує сигнали вибраного гаманця й показує попередню оцінку версії моделі з внеском кожного сигналу; точний збіг OFAC додається як прямий санкційний доказ лише після явної перевірки, відсутність збігу не знижує бал. Compose worker оновлює відстежувані адреси тими самими обмеженими адаптерами провайдерів; див. [опис фонової синхронізації](docs/uk/continuous-sync.md). Граф зв’язків досліджує спрямовані шляхи в EVM, TRON, Solana, XRPL, TON та Aptos до трьох переходів за збереженими подіями відправника й отримувача та позначає невідстежуваних контрагентів. Знімки зберігають ID вихідних спостережень. Зв’язки учасників Cardano однієї транзакції неорієнтовані й не використовуються для пошуку шляхів. Кожен перехід — окреме спостереження; шлях не доводить, що ті самі кошти пройшли весь маршрут. Входи й виходи Bitcoin не визначають контрагентів і не включені до графа. Лічильники та зв’язки огляду будуються зі збережених адрес та історії вибраного розслідування; оцінка балансу й автоматичні мітки недоступні. API не має автентифікації та призначений лише для локальної розробки. Знімок OFAC оновлюється вручну; комерційний сервіс перевірки не підключений.

## Синхронізація історії транзакцій

Ручна синхронізація доступна в інтерфейсі; Compose worker оновлює адреси з цільовим інтервалом п’ять хвилин, якщо провайдер має достатню потужність. Для Bitcoin використовується Blockstream Esplora. Каталог EVM mainnet завантажується через `GET /api/v1/networks`; для Ethereum, Base та Arbitrum зберігаються ID `ethereum`, `base`, `arbitrum`, для інших мереж — `eip155:<chain_id>`. Якщо мережі немає в каталозі Blockscout, використовується фіксований список mainnet Etherscan V2, зокрема BNB Chain, Polygon, OP, Avalanche, Linea та інші. Це не змінює Blockscout для chain ID, який уже є в його каталозі. Etherscan потребує backend-змінну `ETHERSCAN_API_KEY`; для BNB, OP, Avalanche і Gnosis потрібен відповідний платний тариф і `ETHERSCAN_ENABLE_PAID_CHAINS=true`. `history_sync_available` означає налаштований маршрут, але не гарантує відповіді explorer-а чи повноти історії. Див. [інструкцію з фонової синхронізації](docs/uk/continuous-sync.md).

Синхронізація Bitcoin зберігає попередню обмежену поведінку Esplora. Для EVM паралельно завантажуються нативні транзакції, успішні внутрішні перекази нативної валюти та події ERC-20. Зберігаються початкові цілі суми, адреса контракту, необов’язкова кількість decimals, індекс події, адреси сторін, блок, час і хост джерела. Кожен потік Blockscout обмежено 10 сторінками по 50 записів, Etherscan — 10 сторінками по 100 записів; `may_have_more_history` показує, що у провайдера була наступна сторінка. Це обмежений перегляд даних explorer-а, а не повний індекс: покриття та пропуски залежать від мережі й провайдера. Кілька подій однієї транзакції зберігаються окремо. Endpoint переказів повертає до 500 останніх записів. Worker опитує історію, але не відстежує кожен блок або mempool-подію.

TRON mainnet доступна через TronGrid. Задай `TRONGRID_API_KEY` лише на backend: ключ надсилається в заголовку `TRON-PRO-API-KEY` і не має потрапляти до браузерної конфігурації. Адаптер зберігає успішні нативні `TransferContract` та події TRC-20 `Transfer`. Це обмежена історія індексувального провайдера, а не повний індекс мережі: індексація та термін зберігання можуть залишати пропуски; TRC-10, TRC-721, внутрішні TRX-перекази контрактів і семантика інших контрактів не розбираються. Синхронізацію обмежено трьома сторінками до 200 записів на потік; після 403/429 повтор відбудеться під час наступного планового або ручного запуску. Див. [опис синхронізації TRON](docs/uk/continuous-sync.md).

Solana доступна як окрема сім’я мережі через `SOLANA_RPC_URL` (за замовчуванням використовується спільний публічний RPC mainnet Solana). Зберігаються фіналізовані нативні перекази System Program і розібрані SPL Token `transfer` / `transferChecked`, включно з внутрішніми інструкціями, якщо доступні власник token account і mint metadata. Синхронізація йде обмеженими сторінками по 15 підписів. Покриття SPL часткове: `getSignaturesForAddress` повертає транзакції, де запитаний ключ є в `accountKeys`. Тому вхідний SPL-переказ може не потрапити в історію, якщо адреса гаманця є лише в owner metadata балансів токенів. Стандартний RPC також не знаходить повний поточний та історичний перелік token accounts гаманця. Публічний RPC обмежує запити й може не зберігати старі транзакції; інші програми, swaps, NFT/stake та непідтримувані інструкції не охоплені. Для ширшого пошуку за власником потрібен індексувальний провайдер — перевір його покриття й умови. Див. [інструкцію з Solana sync](docs/uk/continuous-sync.md).

## Запуск локального API

Потрібен Docker Compose.

```sh
docker compose --env-file .env.example up --build -d
```

Приклад конфігурації використовує облікові дані лише для локальної розробки. Compose публікує сервіси на loopback; не відкривайте цей API без автентифікації в мережу. Перевірити стан можна за адресами:

- `http://127.0.0.1:8080/health/live`
- `http://127.0.0.1:8080/health/ready` — перевіряє PostgreSQL і Redis.

Зупинити сервіси зі збереженням даних бази можна командою:

```sh
docker compose --env-file .env.example down
```

## Запуск прототипу інтерфейсу

Вимоги: Node.js 20.19+ або 22.12+ та npm.

```sh
npm ci
npm run dev
```

Якщо локальний API та сховища запущені, застосунок за адресою Vite показує збережені дані розслідування. Frontend API-ключ не потрібен.

## Джерела даних і ліцензування

Синхронізація Bitcoin та вибраних EVM-мереж отримує історію через Blockstream Esplora й Blockscout вручну та через фоновий Compose worker. Ці дані описують транзакції, але не атрибутують осіб і не забезпечують повного аналізу ризику гаманців. Можна локально імпортувати офіційний знімок OFAC SDN і виконувати точну перевірку адрес Bitcoin, Ethereum, TRON та XRP Ledger; оновлення виконується вручну. API не використовує вебпошук OFAC для автоматичних запитів ([FAQ OFAC](https://ofac.treasury.gov/faqs/287)). Комерційні аналітичні сервіси потребують окремої ліцензії.

## Безпека та відповідальне використання

Історія Cardano mainnet завантажується через Blockfrost, якщо на backend задано `BLOCKFROST_PROJECT_ID`. Один запуск обмежений 82 логічними операціями (до 164 HTTP-спроб з урахуванням однієї повторної спроби на 429/5xx) і використовує Redis rate gate. Зв’язки Cardano на графі показують лише участь в одній транзакції, а не атрибутований переказ. Обмеження описані в [документації синхронізації Cardano](docs/uk/continuous-sync.md).

Не надсилайте приватні ключі, seed-фрази чи секрети. Tracefold задуманий як watch-only інструмент. Сигнали ризику допомагають почати перевірку, але не є юридичною консультацією, доказом особи чи автоматичною підставою для блокування коштів або відмови в обслуговуванні. Дотримуйтеся чинного законодавства й умов постачальників даних.

Перед повідомленням про вразливість прочитайте [політику безпеки](docs/uk/security.md).

Історія TON mainnet доступна через TON Center API v3 для нативних повідомлень та індексованих Jetton-переказів. Налаштуйте backend-змінні `TONCENTER_BASE_URL` і за потреби `TONCENTER_API_KEY`. Адаптер обмежує сторінки 100 записами на потік, використовує окремі курсори оновлення та backfill і зберігає Jetton у raw units, оскільки decimals не гарантовані. Індексація та глибина зберігання провайдера можуть спричиняти пропуски; це не повний індекс мережі. Див. [опис синхронізації TON](docs/uk/continuous-sync.md).

Aptos використовує офіційний hosted Indexer GraphQL для історії транзакцій акаунта. `APTOS_INDEXER_URL` за замовчуванням вказує на mainnet endpoint; `APTOS_INDEXER_API_KEY` необов’язковий. Адаптер зберігає явні Fungible Asset поповнення та списання і пов’язує контрагента лише за однозначного збігу активності в транзакції. Суми залишаються в raw units. Див. [покриття й обмеження Aptos](docs/uk/aptos-history.md).

Sui використовує офіційний mainnet GraphQL; `SUI_GRAPHQL_URL` можна замінити URL провайдера, а `SUI_GRAPHQL_API_KEY` потрібен лише якщо він вимагає bearer token. Адаптер зберігає зміни балансу, але не стверджує, що вони є прямими переказами. Публічний endpoint обмежений частотою запитів і глибиною історії. Докладніше: [історія та покриття Sui](docs/uk/sui-history.md).
