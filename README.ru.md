# Tracefold

Открытый инструмент для изучения потоков средств между блокчейн-адресами.

> **Статус проекта: ранний прототип.** Основной граф, подписи кошельков и балансы пока содержат демонстрационные данные. Таблица последних транзакций показывает сохранённые наблюдения добавленных кошельков и будет пустой, пока история не синхронизирована через настроенный источник. Панель риска загружает сигналы аналитика для выбранного адреса и может учитывать точное совпадение OFAC SDN после явной проверки локального снимка; версия оценки предварительная и не является юридическим выводом или полной комплаенс-проверкой. В панели кошелька доступна ручная синхронизация. Compose `sync-worker` периодически обновляет отслеживаемые Bitcoin и поддерживаемые EVM-адреса с целевым интервалом пять минут при достаточной мощности провайдера; это ограниченный опрос истории, а не мониторинг в реальном времени или всего mempool. Граф расследования связывает сохранённые события отправителя и получателя из EVM, TRON, Solana и XRPL, исследует пути до трёх переходов и сохраняет снимки с ID источников. Каждый переход — отдельное наблюдение; путь не доказывает, что одни и те же средства прошли весь маршрут. Контрагенты Bitcoin не выводятся. Поддерживаются Ethereum, Base и Arbitrum One. Проверка точного адреса по локально импортированному снимку OFAC SDN доступна для Bitcoin и Ethereum. Не используйте демоданные для операционных или комплаенс-решений.

**Документация:** [Русский](README.ru.md) · [Українська](README.uk.md) · [English](README.md)

Граф расследования использует сохранённые связи отправителя и получателя из EVM, TRON, Solana и XRPL. Снимок фиксирует граф вместе с ID исходных наблюдений и открывается повторно. Ограничения описаны в [документации API снимков](docs/ru/graph-snapshots-api.md).

## О проекте

Tracefold задуман как OSINT-инструмент для расследований. Аналитик сможет начать с адреса, проследить переводы в поддерживаемых сетях, сохранить основания каждой связи и проверить сигналы риска. Алгоритмическая оценка не должна восприниматься как доказательство.

Прототип интерфейса включает демонстрационный обзорный граф и граф связей по сохранённой мультичейн-истории, фильтры сетей, таблицу сохранённых наблюдений и объяснимую версионируемую оценку выбранного сохранённого кошелька.

## Принципы

- Для каждой находки показывать сеть, адрес, ссылку на транзакцию, источник и время наблюдения.
- Разделять наблюдаемые транзакции, пользовательские подписи и гипотезы аналитика.
- Показывать сеть как предположение, которое нужно подтвердить: адрес формата EVM может существовать в Ethereum, Base, Arbitrum и других совместимых сетях.
- Называть оценку индексом подверженности, а не вероятностью или доказательством нарушения.
- Показывать полноту покрытия и актуальность данных; не создавать впечатление, что отслеживаются все кошельки и сети.

## Текущий стек

- **Frontend:** React, TypeScript, Vite и Tailwind CSS.
- **API:** локальный сервис на Rust и Axum.
- **Постоянные данные:** PostgreSQL; начальная миграция создаёт таблицы расследований, отслеживаемых адресов и сигналов риска.
- **Очередь и координация:** Redis Streams для фонового worker-а; API также проверяет доступность Redis в readiness endpoint.

API поддерживает создание и просмотр расследований и отслеживаемых адресов, синхронизацию истории поддерживаемых сетей, сигналы риска, проверку адреса и сохранение снимков графа. Таблица последних транзакций показывает сохранённые наблюдения и их источник. Панель риска загружает сигналы выбранного кошелька и показывает предварительную оценку версии модели с вкладом каждого сигнала; точное совпадение OFAC добавляется как прямое санкционное доказательство только после явной проверки, отсутствие совпадения балл не снижает. Compose worker обновляет отслеживаемые адреса через те же ограниченные адаптеры провайдеров; см. [описание фоновой синхронизации](docs/ru/continuous-sync.md). Граф строит направленные связи по сохранённым событиям EVM, TRON, Solana и XRPL, отмечает контрагентов и сохраняет снимки с ID исходных наблюдений. Каждый переход — отдельное наблюдение; путь не доказывает, что одни и те же средства прошли весь маршрут. Входы и выходы Bitcoin не показывают контрагентов и не включаются в граф. Основной граф и балансы используют демоданные. API не имеет аутентификации и предназначен только для локальной разработки. Снимок OFAC обновляется вручную; коммерческий сервис проверки не подключён.

## Синхронизация истории транзакций

Ручная синхронизация доступна через интерфейс; Compose worker обновляет адреса с целевым интервалом пять минут, если хватает ресурсов провайдера. Для Bitcoin используется Blockstream Esplora. Каталог EVM mainnet загружается через `GET /api/v1/networks`; для Ethereum, Base и Arbitrum сохраняются ID `ethereum`, `base`, `arbitrum`, для остальных сетей — `eip155:<chain_id>`. Если сети нет в каталоге Blockscout, используется фиксированный список mainnet Etherscan V2, включая BNB Chain, Polygon, OP, Avalanche, Linea и другие. Добавление сети не меняет источник Blockscout для уже присутствующего там chain ID. Etherscan требует backend-переменную `ETHERSCAN_API_KEY`; для BNB, OP, Avalanche и Gnosis нужен подходящий платный тариф и `ETHERSCAN_ENABLE_PAID_CHAINS=true`. `history_sync_available` означает настроенный маршрут, но не гарантирует ответ explorer-а или полноту истории. См. [инструкцию по фоновой синхронизации](docs/ru/continuous-sync.md).

Синхронизация Bitcoin сохраняет прежнее ограниченное поведение Esplora. Для EVM параллельно загружаются нативные транзакции, успешные внутренние переводы нативной валюты и события ERC-20. Сохраняются исходные целые суммы, адрес контракта, необязательное число decimals, индекс события, адреса сторон, блок, время и хост источника. Каждый поток Blockscout ограничен 10 страницами по 50 записей, Etherscan — 10 страницами по 100 записей; `may_have_more_history` показывает, что у провайдера была следующая страница. Это ограниченный просмотр данных explorer-а, а не полный индекс: покрытие и пропуски зависят от сети и провайдера. Несколько событий одной транзакции хранятся отдельно. Endpoint переводов возвращает до 500 последних записей. Worker опрашивает историю, но не отслеживает каждый блок или mempool-событие.

TRON mainnet доступна через TronGrid. Задай `TRONGRID_API_KEY` только на backend: ключ отправляется в заголовке `TRON-PRO-API-KEY` и не должен попадать в браузерную конфигурацию. Адаптер сохраняет успешные нативные `TransferContract` и события TRC-20 `Transfer`. Это ограниченная история индексирующего провайдера, а не полный индекс сети: индексация и срок хранения могут оставлять пропуски; TRC-10, TRC-721, внутренние TRX-переводы контрактов и семантика других контрактов не разбираются. Синхронизация ограничена тремя страницами до 200 записей на поток; после 403/429 повтор будет при следующем плановом или ручном запуске. См. [описание синхронизации TRON](docs/ru/continuous-sync.md).

Solana доступна как отдельная семья сети через `SOLANA_RPC_URL` (по умолчанию используется общий публичный RPC mainnet Solana). Сохраняются финализированные нативные переводы System Program и разобранные SPL Token `transfer` / `transferChecked`, включая внутренние инструкции, если доступны владелец token account и mint metadata. Синхронизация идёт ограниченными страницами по 15 подписей. Покрытие SPL частичное: `getSignaturesForAddress` возвращает транзакции, в которых запрошенный ключ присутствует в `accountKeys`. Поэтому входящий SPL-перевод может не попасть в историю, если адрес кошелька встречается только в owner metadata балансов токенов. Стандартный RPC также не обнаруживает полный текущий и исторический набор token accounts кошелька. Публичный RPC ограничивает запросы и может не хранить старые транзакции; другие программы, swaps, NFT/stake и неподдерживаемые инструкции не покрываются. Для более полного поиска по владельцу нужен индексирующий провайдер — проверь его покрытие и условия. См. [инструкцию по Solana sync](docs/ru/continuous-sync.md).

## Запуск локального API

Требуется Docker Compose.

```sh
docker compose --env-file .env.example up --build -d
```

Пример конфигурации использует учётные данные только для локальной разработки. Compose публикует сервисы на loopback; не открывайте этот API без аутентификации в сеть. Проверить состояние можно по адресам:

- `http://127.0.0.1:8080/health/live`
- `http://127.0.0.1:8080/health/ready` — проверяет PostgreSQL и Redis.

Остановить сервисы, сохранив данные базы, можно командой:

```sh
docker compose --env-file .env.example down
```

## Запуск прототипа интерфейса

Требования: Node.js 20.19+ или 22.12+ и npm.

```sh

```

## Источники данных и лицензирование

Синхронизация Bitcoin и выбранных EVM-сетей получает историю через Blockstream Esplora и Blockscout вручную и через фоновый Compose worker. Эти данные описывают транзакции, но не атрибутируют личности и не обеспечивают полный анализ риска кошельков. Можно локально импортировать официальный снимок OFAC SDN и выполнять точную проверку адресов Bitcoin и Ethereum; обновление выполняется вручную. API не использует веб-поиск OFAC для автоматических запросов ([FAQ OFAC](https://ofac.treasury.gov/faqs/287)). Коммерческие аналитические сервисы требуют отдельной лицензии.

## Безопасность и ответственное использование

История Cardano mainnet загружается через Blockfrost, если на backend задан `BLOCKFROST_PROJECT_ID`. Один запуск ограничен 82 логическими операциями (до 164 HTTP-попыток с учётом одной повторной попытки на 429/5xx) и использует Redis rate gate. Связи Cardano в графе показывают только участие в одной транзакции, а не атрибутированный перевод. Ограничения описаны в [документации синхронизации Cardano](docs/ru/continuous-sync.md).

Не отправляйте приватные ключи, seed-фразы и секреты. Tracefold задуман как watch-only инструмент. Сигналы риска помогают начать проверку, но не являются юридической консультацией, доказательством личности или автоматическим основанием для блокировки средств или отказа в обслуживании. Соблюдайте применимое законодательство и условия поставщиков данных.

История TON mainnet доступна через TON Center API v3 для нативных сообщений и индексированных Jetton-переводов. Настройте backend-переменные `TONCENTER_BASE_URL` и при необходимости `TONCENTER_API_KEY`. Адаптер ограничивает страницы 100 записями на поток, использует отдельные курсоры обновления и backfill и сохраняет Jetton в raw units, так как decimals не гарантированы. Индексация и глубина хранения провайдера могут приводить к пропускам; это не полный индекс сети. См. [описание синхронизации TON](docs/ru/continuous-sync.md).

Aptos использует официальный hosted Indexer GraphQL для истории транзакций аккаунта. `APTOS_INDEXER_URL` по умолчанию указывает на mainnet endpoint; `APTOS_INDEXER_API_KEY` необязателен. Адаптер сохраняет явные fungible asset пополнения и списания и связывает контрагента только при однозначном совпадении активности в транзакции. Суммы остаются в raw units. См. [покрытие и ограничения Aptos](docs/ru/aptos-history.md).

История TON mainnet доступна через TON Center API v3 для нативных сообщений и индексированных Jetton-переводов. Настройте backend-переменные `TONCENTER_BASE_URL` и при необходимости `TONCENTER_API_KEY`. Адаптер ограничивает страницы 100 записями на поток, использует отдельные курсоры обновления и backfill и сохраняет Jetton в raw units, так как decimals не гарантированы. Индексация и глубина хранения провайдера могут приводить к пропускам; это не полный индекс сети. См. [описание синхронизации TON](docs/ru/continuous-sync.md).
