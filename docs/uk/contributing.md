# Як долучитися

Дякуємо, що допомагаєте покращувати Tracefold. Зміни мають відокремлювати спостережені факти блокчейну від припущених зв’язків і сигналів ризику.

Інші мови: [English](../../CONTRIBUTING.md) · [Русский](../ru/contributing.md)

## Перед початком

- Перевірте наявні issues і код на схожу функціональність.
- Для значних змін провайдера, схеми чи скорингу спершу створіть issue та опишіть джерело даних і очікуване покриття.
- Не додавайте приватні ключі, seed-фрази, облікові дані провайдера, реальні дані користувачів або неочищені логи до issues, тестів чи fixtures.

## Налаштування розробки

Використовуйте Node.js 22, Rust stable, Docker Compose, PostgreSQL і Redis. Для локальної розробки скопіюйте `.env.example` у `.env`; реальні ключі зберігайте лише в ігнорованому Git файлі `.env`.

```sh
npm ci
docker compose up --build
```

Фронтенд запускається командою `npm run dev`. Compose запускає API, PostgreSQL, Redis і sync worker. Перед змінами потоку даних або провайдерів прочитайте [архітектуру](architecture.md) та [синхронізацію історії](continuous-sync.md).

## Зміни та перевірки

Зосереджуйте кожен pull request на одній задачі. Для змін схеми додавайте міграції, для бізнес-правил, розбору відповідей провайдера, курсорів та важливих помилок — тести. Для кожного провайдера документуйте джерело, ліцензію або умови, ліміти, пагінацію й відомі прогалини покриття.

Перед pull request запустіть відповідні перевірки:

```sh
npm run lint
npm run format:check
npm run test
npm run build
cargo fmt --manifest-path apps/api/Cargo.toml --all -- --check
cargo clippy --manifest-path apps/api/Cargo.toml --all-targets --all-features -- -D warnings
cargo test --manifest-path apps/api/Cargo.toml --all-features
```

Для повного набору Rust integration-тестів потрібні PostgreSQL і Redis. GitHub Actions запускає перевірки фронтенду та Rust API для кожного pull request.

## Чек-лист pull request

- Опишіть поведінку для користувача й обмеження покриття провайдера.
- Додайте посилання на issue або поясніть потребу в зміні.
- Додайте тести й оновіть документацію EN/RU/UK, якщо змінюються поведінка, конфігурація, API чи покриття.
- Переконайтеся, що в Git не потрапили облікові дані, приватні ключі та персональні дані.
- Пишіть коментарі й тексти інтерфейсу фактологічно: risk score визначає пріоритет перевірки, а не звинувачує.
