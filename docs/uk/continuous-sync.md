# Фонова синхронізація історії гаманців

Команда `docker compose up` запускає `sync-worker`, який періодично оновлює історію відстежуваних адрес через адаптери Esplora та Blockscout. Щоб вимкнути фонові запити, виконай `docker compose stop sync-worker`; API й ручна синхронізація продовжать працювати.

## Каталог мереж і вибір провайдера

`GET /api/v1/networks` повертає Bitcoin та EVM mainnet, опубліковані в `/api/json/config` Blockscout. Каталог зберігається в пам’яті шість годин; якщо оновлення не вдалося, використовується останній успішний каталог або вбудовані записи Bitcoin, Ethereum, Base, Arbitrum, Solana та TRON. Старі ID залишаються `bitcoin`, `ethereum`, `base` і `arbitrum`, інші EVM-мережі використовують `eip155:<chain_id>`. Формат EVM-адреси не визначає мережу, тому її потрібно вибрати з каталогу.

Для кожної мережі API використовує перевірений HTTPS URL екземпляра Blockscout із `instance_url_from_config` або explorer, для якого явно вказано `hostedBy: blockscout`. API не надсилає запити на довільні адреси explorer-ів і не переходить за перенаправленнями. Якщо задано `BLOCKSCOUT_API_KEY`, використовується налаштований multichain API; користувацький `BLOCKSCOUT_BASE_URL` також перевизначає адресу джерела. `history_sync_available` означає, що маршрут провайдера налаштований, але доступність не перевірялася. Окремі explorer-и можуть обмежувати запити, блокувати автоматизацію, повертати HTML challenge або неповну історію; такі відповіді дають загальну помилку недоступності провайдера й не зберігаються як спостереження.

Якщо chain ID відсутній у каталозі Blockscout, API може додати мережу з фіксованого списку Etherscan V2 mainnet. Довільні chain ID та URL провайдера з запиту не приймаються, а джерело мереж, уже наявних у каталозі Blockscout, не змінюється. Перелік базується на [офіційному списку підтримуваних мереж Etherscan](https://docs.etherscan.io/supported-chains) і [live chainlist](https://api.etherscan.io/v2/chainlist); він містить BNB Smart Chain, Polygon PoS, OP Mainnet, Avalanche C-Chain, Linea, Celo, Mantle, Gnosis та інші mainnet. Каталог повертає прапорці `requires_api_key` і `requires_paid_tier`. Задай `ETHERSCAN_API_KEY` у backend-оточенні; без ключа мережі залишаються видимими, але `history_sync_available` має значення `false`. Для BNB, OP, Avalanche і Gnosis потрібен платний тариф Etherscan; встановлюй `ETHERSCAN_ENABLE_PAID_CHAINS=true` лише якщо ключ має доступ до цих мереж. За замовчуванням значення `false`, тому платний тариф не впливає на синхронізацію решти мереж. За даними Etherscan HyperEVM (999) доступний безкоштовно до 30 листопада 2026 року, а з 1 грудня потрібен тариф Lite або вище. Від цієї дати каталог встановлює `requires_paid_tier`, а синхронізація потребує явного `ETHERSCAN_ENABLE_PAID_CHAINS=true`. Abstract Mainnet (2741) не включена до статичного резервного списку: Etherscan оголосив припинення підтримки API з 30 листопада 2026 року.

Etherscan V2 запитує `txlist`, `txlistinternal` і `tokentx`: зберігаються нативні транзакції, внутрішні виклики з передачею нативної валюти та перекази ERC-20. NFT-перекази й інші події контрактів не декодуються. Кожен потік обмежений 10 сторінками по 100 записів на синхронізацію. API та sync-worker використовують спільний Redis gate `SET NX PX`, який встановлює інтервал 400 мс для налаштованого API-ключа; якщо Redis недоступний, запит Etherscan не виконується. Це нижче офіційного ліміту безплатного тарифу ([ліміти запитів](https://docs.etherscan.io/rate-limits)); для платних тарифів діє той самий консервативний інтервал. У відповіді `tokentx` провайдер не документує індекс лога; адаптер створює стабільний локальний індекс події з полів переказу, щоб не об’єднувати кілька записів однієї транзакції. Це ключ дедуплікації, а не on-chain log index. Etherscan вимагає передавати API-ключ у query string: зберігай його лише в backend-оточенні, не записуй повні URL запитів у журнали й не додавай ключ у frontend. Налаштований маршрут не гарантує доступ до тарифу, доступність провайдера чи повноту старої історії.

## Історія TRON і покриття

Вбудована мережа `tron` використовує TronGrid mainnet за адресою `https://api.trongrid.io`. За потреби задай `TRONGRID_BASE_URL` як кореневу URL сумісного джерела TronGrid і `TRONGRID_API_KEY`. Ключ backend надсилає лише в заголовку `TRON-PRO-API-KEY`; він не додається до URL і не передається frontend-у. Не додавай `TRON-PRO-API-KEY` до браузерного коду.

Для нативних транзакцій акаунта та історії подій TRC-20 ведуться окремі fingerprint-курсори. Одна синхронізація обмежена трьома сторінками на потік (до 200 записів на сторінці); незавершений catch-up/backfill продовжується під час наступного запуску. Endpoint історії акаунта повертає виклики контрактів та інші типи транзакцій, тому нативний TRX зберігається лише для успішних `TransferContract`. В історії TRC-20 зберігаються лише рядки з типом події `Transfer`; approvals та інші події пропускаються. Адреси джерела перевіряються за checksum і нормалізуються перед порівнянням. Якщо провайдер не повертає документований індекс події/логу, створюється детермінований ідентифікатор події, щоб зберегти кілька подій однієї транзакції.

Це історія індексувального провайдера, а не повний індекс мережі. TronGrid може обмежувати запити, пропускати чи затримувати індексовані рядки; доступність старої історії залежить від зберігання провайдера. Внутрішні TRX-перекази контрактів, TRC-10, TRC-721, swaps і семантика інших контрактів не розбираються. HTTP 403/429 завершує поточну синхронізацію без негайного повтору; worker повторить її за розкладом або користувач може запустити ручну синхронізацію пізніше. Вбудований каталог вказує покриття лише `native-trx` і `trc20`; ознака доступності означає наявність конфігурації адаптера, а не перевірену доступність джерела.

## Історія Solana та покриття

Вбудована мережа Solana використовує `SOLANA_RPC_URL`; за замовчуванням це `https://api.mainnet.solana.com`. Вкажи HTTPS RPC-провайдера, якому довіряєш або яким керуєш. HTTP дозволено лише для loopback-адрес під час локальної розробки. Каталог позначає маршрут як налаштований, але не перевіряє доступність провайдера й не гарантує зберігання архівної історії.

Синхронізація викликає Solana JSON-RPC `getSignaturesForAddress` з рівнем `finalized`, потім отримує транзакцію через `getTransaction` із `jsonParsed` та `maxSupportedTransactionVersion: 0`. Один запуск обробляє не більше 15 підписів і зберігає окремі курсори для нових операцій та backfill. Зберігаються розібрані нативні SOL-події System Program `transfer` і `transferWithSeed`, а також SPL Token / Token-2022 `transfer` і `transferChecked` із зовнішніх та внутрішніх інструкцій у порядку виконання. Власники SPL-рахунків визначаються за відповідними `preTokenBalances` / `postTokenBalances`; неоднозначні записи без даних про власника чи mint пропускаються. Початкові цілі суми зберігаються, decimals беруться з відповіді RPC, якщо вони наявні.

Це не повний індекс Solana, а покриття SPL часткове. Офіційний [`getSignaturesForAddress`](https://solana.com/docs/rpc/http/getsignaturesforaddress) шукає транзакції, де запитаний публічний ключ є в `accountKeys`. Вхідний SPL-переказ може містити адресу гаманця лише як `owner` у metadata балансів токенів, тоді як у ключах транзакції зазначено token account; такий переказ не буде знайдено пошуком за адресою власника. Стандартний RPC також не перелічує повний поточний чи історичний набір token accounts, а закриті token accounts цей сканер відновити не може. Інші програми (зокрема swaps, NFT та staking) і нестандартні інструкції не розбираються. HTTP-помилка публічного RPC завершує поточну синхронізацію; повтор відбудеться під час наступного ручного або планового запуску. Провайдер також може видаляти старі дані ledger. Для ширшого пошуку за власником чи історичних даних токенів використовуй індексувального провайдера та перевір його покриття й умови. Для `getTransaction` використовується документоване значення версії транзакції `0`.

Щоб увімкнути Helius `getTransfersByAddress`, задай `SOLANA_HELIUS_API_KEY`. Якщо ключ задано, цей провайдер замінює звичайний RPC-шлях історії Solana та запитує фіналізовані перекази SOL і SPL за адресою власника, включно з пошуком через token accounts. Ключ надсилається лише на `mainnet.helius-rpc.com` і не зберігається в метаданих переказів. За одну синхронізацію адаптер читає не більше двох сторінок по 100 подій, зберігає початкові цілі суми й decimals, а також курсор останнього слота та курсор backfill. Для Helius діють вимоги облікового запису й обмеження плану; перед увімкненням переглянь [документацію методу Helius](https://www.helius.dev/docs/api-reference/rpc/http/gettransfersbyaddress). Якщо змінну не задано, використовується наявний Solana JSON-RPC.

## Історія XRP Ledger і покриття

Вбудована мережа `xrpl` використовує `XRPL_RPC_URL`; за замовчуванням налаштовано публічний full-history endpoint Ripple `https://s2.ripple.com:51234/`. Для регулярного використання вкажи довірений HTTPS JSON-RPC endpoint. Синхронізація використовує пагінацію `account_tx` з незалежними курсорами: свіжий head scan шукає нові транзакції, очікуваний head marker продовжує наздоганяльне сканування до останньої збереженої транзакції, а окремий обмежений backfill проходить старіші сторінки. За запуск обробляється не більше двох свіжих head-сторінок, однієї сторінки за очікуваним head marker та однієї backfill-сторінки — до 50 транзакцій у кожній. Head checkpoint просувається лише після досягнення попереднього checkpoint. Приймаються лише classic-адреси `r...` із коректною checksum; X-address не підтримується.

Адаптер зберігає лише успішні підтверджені прямі XRP Payment, де відстежувана адреса вказана як `Account` або `Destination`. Сума береться з `meta.delivered_amount`, тому для часткових платежів не використовується запитаний `Amount`; зміни лише через комісію, XRP-резерв, невдалі/непідтверджені транзакції, path payments, платежі у випущеній валюті та інші типи транзакцій пропускаються. Перша версія навмисно обмежена й не заявляє повне покриття активності гаманця або декодування IOU trust line.

`account_tx` повертає лише історію, збережену вибраним сервером. Публічний endpoint може обмежувати запити або бути недоступним і не розрахований на постійне виробниче навантаження; для регулярного моніторингу налаштуй власний або комерційний архівний endpoint. Прапорець доступності каталогу означає наявність маршруту, а не повноту історії ledger. Див. [офіційну довідку account_tx](https://xrpl.org/docs/references/http-websocket-apis/public-api-methods/account-methods/account_tx) і [посібник з історії ledger](https://xrpl.org/docs/concepts/networks-and-servers/ledger-history).

```bash
docker compose up --build
```

Для запуску поза Compose потрібні `DATABASE_URL`, `REDIS_URL`, `BITCOIN_ESPLORA_URL`, `XRPL_RPC_URL`, змінні Blockscout і, за потреби, Etherscan:

```bash
cargo run --manifest-path apps/api/Cargo.toml --bin sync_worker
```

Планувальник сканує адреси пакетами за ключовим індексом до 1 000 записів кожні 30 секунд. Redis Streams зберігає не більше 10 000 очікуваних або активних задач. Адреси дедуплікуються; після ідемпотентного запису в PostgreSQL задача підтверджується. Задачі, що залишилися необробленими після збою worker-а, повторно забираються через 10 хвилин. Помилки провайдера й бази повторюються з експоненційною затримкою від 30 секунд до однієї години. Одна синхронізація обмежена вісьмома хвилинами. Після SIGINT або SIGTERM планування зупиняється, а поточна задача завершується перед виходом.

Цільовий інтервал для адреси — п’ять хвилин, якщо провайдер і worker встигають обробляти навантаження. За великої черги або обмежень провайдера фактичний інтервал збільшиться. Глибина історії обмежена адаптерами: Bitcoin — до 20 сторінок, кожен EVM-потік — до 10 сторінок. Worker не відстежує весь mempool, не атрибутує особи, не зберігає ключі та не підписує транзакції. Пауза окремої адреси поки відсутня: додавання адреси вмикає періодичне читання налаштованого публічного джерела.

Черга працює з доставкою «щонайменше один раз». Повторні задачі безпечні завдяки унікальним ключам і upsert-операціям у базі. У Compose для Redis увімкнене постійне зберігання; зберігайте том Redis під час перезапуску.

## Історія TON і покриття

Вбудована мережа `ton` використовує TON Center API v3: `https://toncenter.com/api/v3`. Налаштуйте backend-змінні `TONCENTER_BASE_URL` та за потреби `TONCENTER_API_KEY`; ключ надсилається лише в заголовку `X-API-Key`. Документація вказує обмеження один запит на секунду без ключа. Friendly-адреси mainnet перевіряються за контрольною сумою і зберігаються у канонічному форматі `workchain:hex`; також приймаються raw-адреси `0:` та `-1:`.

Нативні повідомлення транзакцій та індексовані Jetton-перекази завантажуються окремо через `/transactions` і `/jetton/transfers`. Кожен endpoint запитується сторінками до 100 записів; head і історичний backfill мають незалежні logical-time курсори та обробляють не більше однієї сторінки в кожному напрямку за синхронізацію. Сума Jetton зберігається як ціле raw-значення, оскільки endpoint не гарантує decimals токена. Це історія індексувального провайдера, а не повний індекс мережі: затримки індексації, глибина зберігання та ліміти можуть спричиняти пропуски. Внутрішня логіка контрактів, swaps і довільні payload не інтерпретуються. Див. офіційні [огляд TON Center v3](https://docs.ton.org/ecosystem/api/toncenter/v3/overview), [transactions](https://docs.ton.org/api/v3/blockchain-data/get-transactions) та [Jetton transfers](https://docs.ton.org/ecosystem/api/toncenter/v3/jettons/get-jetton-transfers).

## Історія Cardano mainnet та обмеження атрибуції

Мережа `cardano` доступна, лише якщо backend налаштований через `BLOCKFROST_PROJECT_ID`. Адаптер використовує фіксований API Blockfrost mainnet (`https://cardano-mainnet.blockfrost.io/api/v0`) і передає ключ лише в заголовку `project_id`. Shelley payment-адреси перевіряються за checksum і мережею mainnet; Byron payment-адреси — за checksum і network tag. Stake/reward-адреси та адреси testnet відхиляються. Див. офіційну [документацію Blockfrost API](https://docs.blockfrost.io/).

Синхронізація запитує сторінки по 20 транзакцій і обробляє не більше 20 нових спостережень та 20 записів backfill за запуск. Для кожної транзакції запитується `/txs/{hash}/utxos`; якщо є collateral, також запитується `/txs/{hash}`, щоб розрізнити успішне виконання скрипту й невдале. Один запуск виконує не більше 82 логічних операцій із провайдером: дві сторінки адреси, до 40 запитів UTxO та до 40 запитів для визначення результату скрипту. Оскільки для 429/5xx дозволена одна повторна спроба, абсолютна межа — 164 HTTP-запити на запуск. Спільний Redis gate з інтервалом 120 мс обмежує API та worker з одним ключем. Blockfrost документує ліміт 10 запитів за секунду та може відповідати 402/403/418/429 або 5xx; для 429/5xx виконується одна обмежена повторна спроба, інші помилки зупиняють синхронізацію Cardano. Розмір відповіді обмежений 4 МіБ, сторінка — 20 рядками, набір UTxO — 500 записами на транзакцію. Зберігай ключ і Redis URL у backend environment.

Cardano використовує UTxO: транзакція може витрачати кілька входів і створювати кілька виходів, тому історія адреси не доводить прямої пари відправник–отримувач і не підтверджує володіння іншими входами. Адаптер зберігає валові суми входів і виходів відстежуваної адреси за кожним активом, залишаючи `from_address` і `to_address` порожніми. Інші ефективні входи й виходи зберігаються як зв’язки `same_transaction`. Граф показує їх ненаправлено, без суми; вони не беруть участі в пошуку направлених шляхів або оцінці швидкого обігу. Reference inputs ігноруються. Для невдалих script-транзакцій враховуються лише collateral inputs/outputs; якщо провайдер не підтвердив результат, транзакція не записується як нульова зміна. ADA має 6 decimals. Native assets Cardano зберігають точне raw-значення та ідентифікатор policy ID + asset name; decimals не вгадуються без metadata. Це обмежена історія провайдера, а не повний індекс мережі; строк зберігання й затримки індексації можуть спричиняти пропуски.
