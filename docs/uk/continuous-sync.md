# Фонова синхронізація історії гаманців

Команда `docker compose up` запускає `sync-worker`, який періодично оновлює історію відстежуваних адрес через адаптери Esplora та Blockscout. Щоб вимкнути фонові запити, виконай `docker compose stop sync-worker`; API й ручна синхронізація продовжать працювати.

## Каталог мереж і вибір провайдера

`GET /api/v1/networks` повертає Bitcoin та EVM mainnet, опубліковані в `/api/json/config` Blockscout. Каталог зберігається в пам’яті шість годин; якщо оновлення не вдалося, використовується останній успішний каталог або вбудовані записи Bitcoin, Ethereum, Base, Arbitrum, Solana та TRON. Старі ID залишаються `bitcoin`, `ethereum`, `base` і `arbitrum`, інші EVM-мережі використовують `eip155:<chain_id>`. Формат EVM-адреси не визначає мережу, тому її потрібно вибрати з каталогу.

Для кожної мережі API використовує перевірений HTTPS URL екземпляра Blockscout із `instance_url_from_config` або explorer, для якого явно вказано `hostedBy: blockscout`. API не надсилає запити на довільні адреси explorer-ів і не переходить за перенаправленнями. Якщо задано `BLOCKSCOUT_API_KEY`, використовується налаштований multichain API; користувацький `BLOCKSCOUT_BASE_URL` також перевизначає адресу джерела. `history_sync_available` означає, що маршрут провайдера налаштований, але доступність не перевірялася. Окремі explorer-и можуть обмежувати запити, блокувати автоматизацію, повертати HTML challenge або неповну історію; такі відповіді дають загальну помилку недоступності провайдера й не зберігаються як спостереження.

## Історія TRON і покриття

Вбудована мережа `tron` використовує TronGrid mainnet за адресою `https://api.trongrid.io`. За потреби задай `TRONGRID_BASE_URL` як кореневу URL сумісного джерела TronGrid і `TRONGRID_API_KEY`. Ключ backend надсилає лише в заголовку `TRON-PRO-API-KEY`; він не додається до URL і не передається frontend-у. Не додавай `TRON-PRO-API-KEY` до браузерного коду.

Для нативних транзакцій акаунта та історії подій TRC-20 ведуться окремі fingerprint-курсори. Одна синхронізація обмежена трьома сторінками на потік (до 200 записів на сторінці); незавершений catch-up/backfill продовжується під час наступного запуску. Endpoint історії акаунта повертає виклики контрактів та інші типи транзакцій, тому нативний TRX зберігається лише для успішних `TransferContract`. В історії TRC-20 зберігаються лише рядки з типом події `Transfer`; approvals та інші події пропускаються. Адреси джерела перевіряються за checksum і нормалізуються перед порівнянням. Якщо провайдер не повертає документований індекс події/логу, створюється детермінований ідентифікатор події, щоб зберегти кілька подій однієї транзакції.

Це історія індексувального провайдера, а не повний індекс мережі. TronGrid може обмежувати запити, пропускати чи затримувати індексовані рядки; доступність старої історії залежить від зберігання провайдера. Внутрішні TRX-перекази контрактів, TRC-10, TRC-721, swaps і семантика інших контрактів не розбираються. HTTP 403/429 завершує поточну синхронізацію без негайного повтору; worker повторить її за розкладом або користувач може запустити ручну синхронізацію пізніше. Вбудований каталог вказує покриття лише `native-trx` і `trc20`; ознака доступності означає наявність конфігурації адаптера, а не перевірену доступність джерела.

## Історія Solana та покриття

Вбудована мережа Solana використовує `SOLANA_RPC_URL`; за замовчуванням це `https://api.mainnet.solana.com`. Вкажи HTTPS RPC-провайдера, якому довіряєш або яким керуєш. HTTP дозволено лише для loopback-адрес під час локальної розробки. Каталог позначає маршрут як налаштований, але не перевіряє доступність провайдера й не гарантує зберігання архівної історії.

Синхронізація викликає Solana JSON-RPC `getSignaturesForAddress` з рівнем `finalized`, потім отримує транзакцію через `getTransaction` із `jsonParsed` та `maxSupportedTransactionVersion: 0`. Один запуск обробляє не більше 15 підписів і зберігає окремі курсори для нових операцій та backfill. Зберігаються розібрані нативні SOL-події System Program `transfer` і `transferWithSeed`, а також SPL Token / Token-2022 `transfer` і `transferChecked` із зовнішніх та внутрішніх інструкцій у порядку виконання. Власники SPL-рахунків визначаються за відповідними `preTokenBalances` / `postTokenBalances`; неоднозначні записи без даних про власника чи mint пропускаються. Початкові цілі суми зберігаються, decimals беруться з відповіді RPC, якщо вони наявні.

Це не повний індекс Solana, а покриття SPL часткове. Офіційний [`getSignaturesForAddress`](https://solana.com/docs/rpc/http/getsignaturesforaddress) шукає транзакції, де запитаний публічний ключ є в `accountKeys`. Вхідний SPL-переказ може містити адресу гаманця лише як `owner` у metadata балансів токенів, тоді як у ключах транзакції зазначено token account; такий переказ не буде знайдено пошуком за адресою власника. Стандартний RPC також не перелічує повний поточний чи історичний набір token accounts, а закриті token accounts цей сканер відновити не може. Інші програми (зокрема swaps, NFT та staking) і нестандартні інструкції не розбираються. HTTP-помилка публічного RPC завершує поточну синхронізацію; повтор відбудеться під час наступного ручного або планового запуску. Провайдер також може видаляти старі дані ledger. Для ширшого пошуку за власником чи історичних даних токенів використовуй індексувального провайдера та перевір його покриття й умови. Для `getTransaction` використовується документоване значення версії транзакції `0`.

```bash
docker compose up --build
```

Для запуску поза Compose потрібні ті самі `DATABASE_URL`, `REDIS_URL`, `BITCOIN_ESPLORA_URL` і змінні Blockscout:

```bash
cargo run --manifest-path apps/api/Cargo.toml --bin sync_worker
```

Планувальник сканує адреси пакетами за ключовим індексом до 1 000 записів кожні 30 секунд. Redis Streams зберігає не більше 10 000 очікуваних або активних задач. Адреси дедуплікуються; після ідемпотентного запису в PostgreSQL задача підтверджується. Задачі, що залишилися необробленими після збою worker-а, повторно забираються через 10 хвилин. Помилки провайдера й бази повторюються з експоненційною затримкою від 30 секунд до однієї години. Одна синхронізація обмежена вісьмома хвилинами. Після SIGINT або SIGTERM планування зупиняється, а поточна задача завершується перед виходом.

Цільовий інтервал для адреси — п’ять хвилин, якщо провайдер і worker встигають обробляти навантаження. За великої черги або обмежень провайдера фактичний інтервал збільшиться. Глибина історії обмежена адаптерами: Bitcoin — до 20 сторінок, кожен EVM-потік — до 10 сторінок. Worker не відстежує весь mempool, не атрибутує особи, не зберігає ключі та не підписує транзакції. Пауза окремої адреси поки відсутня: додавання адреси вмикає періодичне читання налаштованого публічного джерела.

Черга працює з доставкою «щонайменше один раз». Повторні задачі безпечні завдяки унікальним ключам і upsert-операціям у базі. У Compose для Redis увімкнене постійне зберігання; зберігайте том Redis під час перезапуску.
