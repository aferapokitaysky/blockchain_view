# Архітектура

## Поточна реалізація

У репозиторії є frontend на React, TypeScript, Vite та Tailwind і локальний API на Rust/Axum.

- Форма додавання гаманця розпізнає формат адреси Bitcoin, просить обрати мережу для неоднозначної EVM-адреси та зберігає розслідування й адреси через локальний API.
- Оглядовий граф, баланси й мітки вузлів поки використовують статичні демодані. Таблиця останніх транзакцій показує збережені спостереження відстежуваних гаманців: джерело, адресу, суму, статус і час. Панель ризику завантажує сигнали аналітика для вибраного збереженого гаманця й показує попередню оцінку версії моделі з внеском кожного сигналу. Граф розслідування будується за збереженими полями відправника й отримувача EVM, TRON, Solana та XRPL, досліджує спрямовані шляхи до трьох переходів, позначає контрагентів і дозволяє зберігати та відкривати знімки з ID джерел. Кожен перехід — окреме спостереження; шлях не доводить, що ті самі кошти пройшли весь маршрут. Входи й виходи Bitcoin не визначають контрагентів і не включені до цього графа.
- PostgreSQL — постійне сховище. Міграції створюють `investigations`, `tracked_addresses`, `risk_signals` і `observed_transfers`.
- Redis підключений до перевірки готовності API та зберігає чергу фонової синхронізації історії.
- API не має автентифікації та призначений лише для локальної розробки.

## Потік API та зберігання даних

```text
Форма гаманця / локальний запит API
                    |
               Rust + Axum
             /      |       \
     PostgreSQL  Redis Streams  Налаштовані провайдери мереж
       записи    черга sync      історія на запит і у фоні
```

API створює розслідування й відстежувані адреси та показує їхні списки. Ручний запит `POST` на синхронізацію отримує історію Bitcoin-адреси у налаштованого Esplora-сумісного сервісу, нормалізує активність адреси й оновлює записи переказів у PostgreSQL. Окремий `GET` повертає до 500 останніх збережених записів для адреси.

Для кожної транзакції зберігаються налаштований хост Esplora, час спостереження, хеш транзакції, статус підтвердження, метадані блока й суми входів/виходів для відстежуваної адреси. `spent_amount` — сума входів, віднесених до адреси; `received_amount` — сума виходів на цю адресу. Суми зберігаються в цілих сатоші та серіалізуються як рядки, щоб уникнути втрати точності. Це окремі суми входів і виходів, а не зміна балансу.

API сигналів ризику зберігає введені аналітиком відомості в межах розслідування та відстежуваної адреси. Кожен запит перевіряє обидва ID шляху щодо одного запису адреси. У сигналі зберігаються ключ, категорія, серйозність, назва й посилання джерела, час спостереження, структуровані деталі й час створення. Розмір тіла запиту обмежений 16 КіБ, а `details` — 8 КіБ. Ці записи не завантажуються й не перевіряються автоматично; frontend враховує їх у provisional-оцінці вибраного гаманця. Див. [версію моделі та обмеження](risk-model.md).

Знімки графа належать одному розслідуванню. API перевіряє належність вихідних спостережень, зберігає представлення графа, фокус і глибину шляху та повертає до 100 знімків. Тіло запиту обмежене 2 МіБ, JSON графа — 1 МіБ. Див. [API знімків графа](graph-snapshots-api.md).

## Джерело даних і обмеження

- Історію Bitcoin і вибраних EVM-мереж можна завантажувати на запит і фоновим worker-ом.
- Синхронізація запитує початкову сторінку історії Esplora, де можуть бути непідтверджені mempool-транзакції, а потім проходить не більш як 20 сторінок підтвердженої історії. Це до 500 підтверджених транзакцій плюс можливі mempool-записи з початкової відповіді.
- Endpoint переказів повертає не більш як 500 останніх записів. Якщо початкова сторінка містить mempool-записи, синхронізація може завантажити понад 500 рядків; endpoint читання показує обмежений список останніх записів.
- Історія Bitcoin синхронізується через Esplora. Історія EVM завантажується з Blockscout для Ethereum (1), Base (8453) та Arbitrum One (42161): звичайні нативні транзакції, успішні внутрішні перекази нативної валюти й події ERC-20. Кожен потік обмежений 10 сторінками по 50 записів; `may_have_more_history` повідомляє про наступну сторінку на ліміті. Ці обмеження діють і для ручних запитів, і для фонового worker-а. Це не повний індекс і не атрибуція особи; інші EVM-мережі та стандарти токенів не охоплені.
- Перевірка точної адреси виконується за локально імпортованим знімком OFAC SDN для Bitcoin та Ethereum. Фонового оновлення й пошуку непрямої експозиції немає; API повертає дату публікації, щоб було видно актуальність знімка. Після явної перевірки точний збіг додається в UI як прямий критичний доказ; відсутність збігу не знижує оцінку.

Додатковий worker кожні 30 секунд сканує адреси пакетами, ставить дедупліковані задачі в обмежений Redis Stream і викликає ту саму синхронізацію провайдерів, що й ручний endpoint. Див. [інструкцію з фонової синхронізації](continuous-sync.md).

## Мережа й адреси

Рядок адреси сам по собі ненадійно визначає мережу. Для кожної адреси й транзакції потрібно зберігати ідентифікатор мережі. Bitcoin-адреса перевіряється за форматом основної мережі. EVM-адреса може бути валідною в кількох мережах, тому інтерфейс просить обрати мережу; формат не відрізняє Ethereum від Base чи Arbitrum. API нормалізує EVM-адресу, але не визначає мережу автоматично.

## Надійність і безпека

- Перевіряйте вхідні дані та зберігайте зв’язок адреси з розслідуванням у кожному запиті.
- Обмежуйте час запитів до постачальника й використовуйте ідемпотентний запис за адресою та хешем транзакції.
- Зберігайте джерело й час спостереження, щоб аналітик міг перевірити походження та актуальність даних.
- Для локального використання API прив’язаний до loopback. Він не має автентифікації; не відкривайте його в недовірену мережу.
- Чітко відокремлюйте демодані інтерфейсу від спостережень постачальника: оглядовий граф лишається демо, таблиця останніх транзакцій показує збережені спостереження, а дослідник шляхів використовує збережені події EVM, TRON, Solana та XRPL з полями `from_address` → `to_address`. Не сприймайте шлях із кількох переходів як доказ безперервного руху тих самих коштів.
