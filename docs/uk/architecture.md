# Архітектура

## Поточний стан

У репозиторії наразі є прототип інтерфейсу на React, TypeScript, Vite та Tailwind. Гаманці, ребра графа, баланси, рядки переказів, мітки мереж і сигнали ризику — статичні демонстраційні дані у frontend. API, завантаження даних із блокчейнів, атрибуції та підключених джерел поки немає.

## Цільова схема

```text
RPC мереж / індексовані дані / ліцензовані джерела
                           |
                     адаптери даних
                           |
          Rust API та фонові обробники
                  /                 \
           PostgreSQL              Redis
        дані й докази          кеш і координація
                  \                 /
              інтерфейс React / TypeScript
```

- **React і TypeScript** відображають розслідування та забезпечують швидку взаємодію.
- **Rust і Axum** — запланований шар API та обробки. Розбір, нормалізація й запити графа мають проходити через чіткі межі сервісів.
- **PostgreSQL** зберігає розслідування, гаманці, перекази, спостереження джерел і нотатки аналітика. Похідні записи мають зберігати походження й час.
- **Redis** призначений для кешу з TTL, координації обмежень запитів і фонових завдань. Це не єдине сховище доказів.
- **Адаптери джерел** ізолюють API мереж і сторонні набори даних. Кожен адаптер має повідомляти покриття, час останньої успішної синхронізації, ліцензійні умови й помилки постачальника.

## Ідентифікація адреси й мережі

Рядка адреси недостатньо, щоб надійно визначити мережу. Зберігайте ідентифікатор мережі разом із кожною адресою та транзакцією. EVM-адреси синтаксично підходять для багатьох мереж, тому розпізнавання формату може запропонувати сімейство EVM, але не може надійно вибрати Ethereum, Base, Arbitrum чи іншу мережу. Пропонуйте користувачу підтвердити мережу, якщо її не можна визначити з надійного контексту.

Нормалізуйте адреси за правилами конкретної мережі. Зберігайте початкове відображуване значення та не об’єднуйте сутності лише через збіг рядків адрес.

## Модель доказів і графа

Ребро графа має посилатися на транзакцію мережі та зберігати напрямок, актив, суму, час блока або події, час завантаження й джерело. Мітки та кластери сутностей зберігайте як окремі твердження з автором, джерелом, упевненістю й часом спостереження. Не змінюйте спостережуваний переказ так, щоб він виглядав висновком аналітика.

Обмежуйте запити мережею, часовим проміжком, кількістю переходів і розміром результату. Розбивайте великі списки транзакцій на сторінки й повідомляйте, якщо результат неповний або застарілий.

## Надійність і безпека

- Перевіряйте вхідні дані та права користувача на розслідування в API.
- Використовуйте тайм-аути й обмежені повтори для зовнішніх джерел; дотримуйтеся лімітів постачальника.
- Зберігайте облікові дані лише на сервері й не записуйте їх у журнали.
- Робіть завантаження ідемпотентним за мережевими ідентифікаторами транзакцій і подій.
- Вважайте кеш тимчасовим і показуйте його вік.
- Чітко відокремлюйте демонстраційні дані від даних підключених джерел.
