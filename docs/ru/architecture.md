# Архитектура

## Текущая реализация

В репозитории есть frontend на React, TypeScript, Vite и Tailwind и локальный API на Rust/Axum.

- Форма добавления кошелька распознаёт формат адреса Bitcoin, просит выбрать сеть для неоднозначного EVM-адреса и сохраняет расследования и адреса через локальный API.
- Обзорный граф, балансы и подписи узлов пока используют статические демоданные. Таблица последних транзакций показывает сохранённые наблюдения отслеживаемых кошельков: источник, адрес, сумму, статус и время. Панель риска загружает сигналы аналитика для выбранного сохранённого кошелька и показывает предварительную оценку версии модели с вкладом каждого сигнала. В панели сохранённых адресов есть отдельный граф связей по сохранённым полям EVM-отправителя и получателя; он исследует направленные пути до трёх переходов и отмечает неотслеживаемых контрагентов. Каждый переход — отдельное наблюдение; путь не доказывает, что одни и те же средства прошли весь маршрут. Входы и выходы Bitcoin не определяют контрагентов и в этот граф не включаются.
- PostgreSQL — постоянное хранилище. Миграции создают `investigations`, `tracked_addresses`, `risk_signals` и `observed_transfers`.
- Redis подключён к проверке готовности API и хранит очередь фоновой синхронизации истории.
- API без аутентификации и предназначен только для локальной разработки.

## Поток API и хранения данных

```text
Форма кошелька / локальный запрос API
                    |
               Rust + Axum
             /      |       \
     PostgreSQL  Redis Streams  Настроенные провайдеры сети
       записи    очередь sync    история по запросу и в фоне
```

API создаёт расследования и отслеживаемые адреса и выводит их списки. Ручной запрос `POST` получает историю Bitcoin через настроенный Esplora-совместимый сервис или поддерживаемую EVM-историю через Blockscout, нормализует активность адреса и обновляет записи переводов в PostgreSQL. Для EVM сохраняются идентификатор события и адреса отправителя и получателя. Отдельный `GET` возвращает до 500 последних сохранённых записей для адреса.

Для каждой транзакции сохраняются настроенный хост Esplora, время наблюдения, хеш транзакции, статус подтверждения, метаданные блока и суммы входов/выходов для отслеживаемого адреса. `spent_amount` — сумма входов, отнесённых к адресу; `received_amount` — сумма выходов на этот адрес. Суммы хранятся в целых сатоши и сериализуются строками, чтобы не терять точность. Это отдельные суммы входов и выходов, а не изменение баланса.

API сигналов риска сохраняет введённые аналитиком сведения в рамках расследования и отслеживаемого адреса. Каждый запрос проверяет оба ID пути относительно одной записи адреса. В сигнале остаются ключ, категория, серьёзность, имя и ссылка на источник, время наблюдения, структурированные детали и время создания. Размер тела запроса ограничен 16 КиБ, а `details` — 8 КиБ. Эти записи не загружаются и не проверяются автоматически; frontend учитывает их в provisional-оценке выбранного кошелька. См. [версию модели и ограничения](risk-model.md).

Проверка OFAC SDN использует XML-снимок, который отдельная команда импортирует в PostgreSQL. Endpoint возвращает точное совпадение, дату публикации и импорта снимка либо явный статус неподдерживаемой сети или отсутствующего снимка. Bitcoin сопоставляется с валютой `XBT`, Ethereum — с `ETH`; для Base и Arbitrum возвращается `network_not_covered`. После явной проверки точное совпадение добавляется в UI как прямое критическое доказательство; отсутствие совпадения не уменьшает оценку. См. [инструкцию по проверке OFAC](ofac-screening.md).

Дополнительный worker каждые 30 секунд сканирует отслеживаемые адреса пакетами, ставит дедуплицированные задачи в ограниченный Redis Stream и вызывает ту же синхронизацию провайдеров, что и ручной endpoint. См. [инструкцию по фоновой синхронизации](continuous-sync.md).

## Источник данных и ограничения

- Историю Bitcoin и выбранных EVM-сетей можно загружать по запросу и фоновым worker-ом.
- Синхронизация запрашивает начальную страницу истории Esplora, где могут быть неподтверждённые mempool-транзакции, а затем проходит не более 20 страниц подтверждённой истории. Это до 500 подтверждённых транзакций плюс возможные mempool-записи из начального ответа.
- Endpoint переводов возвращает не более 500 последних записей. Если начальная страница содержит mempool-записи, синхронизация может загрузить больше 500 строк; endpoint чтения показывает ограниченный недавний список.
- История Bitcoin синхронизируется через Esplora. История EVM загружается из Blockscout для Ethereum (1), Base (8453) и Arbitrum One (42161): обычные нативные транзакции, успешные внутренние переводы нативной валюты и события ERC-20. Каждый поток ограничен 10 страницами по 50 записей; `may_have_more_history` сообщает о следующей странице на лимите. Эти ограничения действуют и для ручных запросов, и для фонового worker-а. Это не полный индекс и не атрибуция личности; другие EVM-сети и стандарты токенов не входят в покрытие.
- API поддерживает создание, просмотр, замену и удаление сигналов, введённых аналитиком. Проверка точного адреса выполняется по локально импортированному снимку OFAC SDN для Bitcoin и Ethereum. Фонового обновления и поиска косвенной экспозиции нет; API возвращает дату публикации, чтобы была видна актуальность снимка. После явной проверки точное совпадение добавляется в UI как прямое критическое доказательство; отсутствие совпадения не уменьшает оценку.

## Сеть и адреса

Строка адреса сама по себе не определяет сеть надёжно. Для каждого адреса и каждой транзакции нужно хранить идентификатор сети. Bitcoin-адрес проверяется по формату основной сети. EVM-адрес может быть валиден в нескольких сетях, поэтому интерфейс просит выбрать сеть; формат не отличает Ethereum от Base или Arbitrum. API нормализует EVM-адрес, но не определяет сеть автоматически.

## Надёжность и безопасность

- Проверяйте входные данные и сохраняйте связь адреса с расследованием в каждом запросе.
- Ограничивайте время запросов поставщика и используйте идемпотентную запись по адресу и хешу транзакции.
- Сохраняйте источник и время наблюдения, чтобы аналитик мог проверить происхождение и актуальность данных.
- Для локального использования API привязан к loopback. У него нет аутентификации; не открывайте его в недоверенную сеть.
- Явно отделяйте демоданные интерфейса от наблюдений поставщика: обзорный граф остаётся демо, таблица последних транзакций показывает сохранённые наблюдения, а исследователь путей использует только сохранённые EVM-события `from_address` → `to_address`. Не трактуйте путь из нескольких переходов как подтверждение непрерывного движения одних и тех же средств.
