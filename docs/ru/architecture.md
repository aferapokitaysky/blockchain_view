# Архитектура

## Текущее состояние

В репозитории сейчас есть прототип интерфейса на React, TypeScript, Vite и Tailwind. Кошельки, рёбра графа, балансы, строки переводов, подписи сетей и сигналы риска — статические демонстрационные данные во frontend. API, загрузки данных из блокчейнов, атрибуции и подключённых источников пока нет.

## Целевая схема

```text
RPC сетей / индексированные данные / лицензированные источники
                              |
                       адаптеры данных
                              |
             Rust API и фоновые обработчики
                    /                 \
             PostgreSQL              Redis
        данные и доказательства   кэш и координация
                    \                 /
                интерфейс React / TypeScript
```

- **React и TypeScript** отображают расследования и обеспечивают отзывчивое взаимодействие.
- **Rust и Axum** — планируемый слой API и обработки. Разбор, нормализация и запросы графа должны иметь явные границы сервисов.
- **PostgreSQL** хранит расследования, кошельки, переводы, наблюдения источников и заметки аналитика. Производные записи должны сохранять происхождение и время.
- **Redis** предназначен для кэша с TTL, координации ограничений запросов и фоновых задач. Это не единственное хранилище доказательств.
- **Адаптеры источников** изолируют API сетей и сторонние наборы данных. Каждый адаптер должен сообщать покрытие, время последней успешной синхронизации, лицензионные условия и ошибки поставщика.

## Идентификация адреса и сети

Строки адреса недостаточно, чтобы надёжно определить сеть. Сохраняйте идентификатор сети вместе с каждым адресом и транзакцией. EVM-адреса синтаксически подходят для многих сетей, поэтому распознавание формата может предложить семейство EVM, но не может надёжно выбрать Ethereum, Base, Arbitrum или другую сеть. Предлагайте пользователю подтвердить сеть, если её нельзя определить из достоверного контекста.

Нормализуйте адреса по правилам конкретной сети. Сохраняйте исходное отображаемое значение и не объединяйте сущности только из-за совпадения строки адреса.

## Модель доказательств и графа

Ребро графа должно ссылаться на транзакцию сети и хранить направление, актив, сумму, время блока или события, время загрузки и источник. Метки и кластеры сущностей храните как отдельные утверждения с автором, источником, уверенностью и временем наблюдения. Не изменяйте наблюдаемый перевод так, чтобы он выглядел выводом аналитика.

Ограничивайте запросы сетью, временным диапазоном, количеством переходов и размером результата. Разбивайте большие списки транзакций на страницы и сообщайте, если результат неполный или устарел.

## Надёжность и безопасность

- Проверяйте входные данные и права доступа пользователя к расследованию на API.
- Используйте таймауты и ограниченные повторы для внешних источников; соблюдайте лимиты поставщика.
- Храните учётные данные только на сервере и не записывайте их в логи.
- Делайте загрузку идемпотентной через сетевые идентификаторы транзакций и событий.
- Считайте кэш временным и показывайте его возраст.
- Явно отделяйте демонстрационные данные от данных подключённых источников.
