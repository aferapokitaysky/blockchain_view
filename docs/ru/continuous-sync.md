# Фоновая синхронизация истории кошельков

Команда `docker compose up` запускает `sync-worker`, который периодически обновляет историю отслеживаемых адресов через адаптеры Esplora и Blockscout. Чтобы отключить фоновые запросы, выполни `docker compose stop sync-worker`; API и ручная синхронизация продолжат работать.

## Каталог сетей и выбор провайдера

`GET /api/v1/networks` возвращает Bitcoin и EVM mainnet, опубликованные в `/api/json/config` Blockscout. Каталог хранится в памяти шесть часов; при ошибке обновления используется последний успешный каталог или встроенные записи Bitcoin, Ethereum, Base, Arbitrum, Solana и TRON. Старые ID остаются `bitcoin`, `ethereum`, `base` и `arbitrum`, другие EVM-сети используют `eip155:<chain_id>`. Формат EVM-адреса не определяет сеть, поэтому её нужно выбрать из каталога.

Для каждой сети API использует проверенный HTTPS URL экземпляра Blockscout из `instance_url_from_config` либо explorer, для которого явно указано `hostedBy: blockscout`. API не отправляет запросы на произвольные адреса explorer-ов и не следует перенаправлениям. Если задан `BLOCKSCOUT_API_KEY`, используется настроенный multichain API; пользовательский `BLOCKSCOUT_BASE_URL` также переопределяет адрес источника. `history_sync_available` означает, что маршрут провайдера настроен, но не прошёл проверку доступности. Отдельные explorer-ы могут ограничивать запросы, блокировать автоматизацию, возвращать HTML challenge или неполную историю; такие ответы дают общую ошибку недоступности провайдера и не сохраняются как наблюдения.

## История TRON и покрытие

Встроенная сеть `tron` использует TronGrid mainnet с адресом `https://api.trongrid.io`. При необходимости задай `TRONGRID_BASE_URL` как корневой URL совместимого источника TronGrid и `TRONGRID_API_KEY`. Ключ передаётся только backend-ом в заголовке `TRON-PRO-API-KEY`; он не добавляется в URL и не передаётся frontend-у. Не помещай `TRON-PRO-API-KEY` в браузерный код.

Для нативных транзакций аккаунта и истории событий TRC-20 ведутся отдельные fingerprint-курсоры. Одна синхронизация ограничена тремя страницами на поток (до 200 записей на странице); незавершённый catch-up/backfill продолжается при следующем запуске. Endpoint истории аккаунта возвращает вызовы контрактов и другие типы транзакций, поэтому нативный TRX сохраняется только для успешных `TransferContract`. В истории TRC-20 сохраняются только строки с типом события `Transfer`; approvals и другие события пропускаются. Адреса источника проверяются по checksum и нормализуются перед сравнением. Если провайдер не отдаёт документированный индекс события/лога, создаётся детерминированный идентификатор события, чтобы сохранить несколько событий одной транзакции.

Это история индексирующего провайдера, а не полный индекс сети. TronGrid может ограничивать запросы, пропускать или задерживать индексированные строки; доступность старой истории зависит от хранения провайдера. Внутренние TRX-переводы контрактов, TRC-10, TRC-721, swaps и семантика других контрактов не разбираются. HTTP 403/429 завершает текущую синхронизацию без немедленного повтора; worker повторит её по расписанию, либо пользователь может запустить ручную синхронизацию позже. Встроенный каталог указывает покрытие только `native-trx` и `trc20`; признак доступности означает наличие конфигурации адаптера, а не проверенную доступность источника.

## История Solana и покрытие

Встроенная сеть Solana использует `SOLANA_RPC_URL`; по умолчанию это `https://api.mainnet.solana.com`. Укажи HTTPS RPC-провайдера, которому доверяешь или которым управляешь. HTTP разрешён только для loopback-адресов при локальной разработке. Каталог помечает маршрут как настроенный, но не проверяет доступность провайдера и не гарантирует хранение архивной истории.

Синхронизация вызывает Solana JSON-RPC `getSignaturesForAddress` с уровнем `finalized`, затем получает транзакцию через `getTransaction` с `jsonParsed` и `maxSupportedTransactionVersion: 0`. Один запуск обрабатывает не более 15 подписей и сохраняет отдельные курсоры для новых операций и backfill. Сохраняются разобранные нативные SOL-события System Program `transfer` и `transferWithSeed`, а также SPL Token / Token-2022 `transfer` и `transferChecked` из внешних и внутренних инструкций в порядке их исполнения. Владельцы SPL-счетов определяются по совпадающим `preTokenBalances` / `postTokenBalances`; неоднозначные записи без данных о владельце или mint пропускаются. Начальные целые суммы сохраняются, decimals берутся из ответа RPC, если они присутствуют.

Это не полный индекс Solana, а покрытие SPL частичное. Официальный [`getSignaturesForAddress`](https://solana.com/docs/rpc/http/getsignaturesforaddress) ищет транзакции, где запрошенный публичный ключ есть в `accountKeys`. Входящий SPL-перевод может содержать адрес кошелька только как `owner` в metadata балансов токенов, тогда как в ключах транзакции указан token account; такой перевод не будет найден поиском по адресу владельца. Стандартный RPC также не перечисляет полный текущий или исторический набор token accounts, а закрытые token accounts этим сканером восстановить нельзя. Другие программы (включая swaps, NFT и staking) и нестандартные инструкции не разбираются. HTTP-ошибка публичного RPC завершает текущую синхронизацию; повтор будет при следующем ручном или плановом запуске. Провайдер также может удалять старые данные ledger. Для более широкого поиска по владельцу или исторических токеновых данных используй индексирующего провайдера и проверь его покрытие и условия. Для `getTransaction` используется документированное значение версии транзакции `0`.

```bash
docker compose up --build
```

Для запуска вне Compose нужны те же `DATABASE_URL`, `REDIS_URL`, `BITCOIN_ESPLORA_URL` и переменные Blockscout:

```bash
cargo run --manifest-path apps/api/Cargo.toml --bin sync_worker
```

Планировщик сканирует адреса пакетами по ключевому индексу до 1 000 записей каждые 30 секунд. Redis Streams хранит не более 10 000 ожидающих или выполняемых задач. Адреса дедуплицируются; после идемпотентной записи в PostgreSQL задача подтверждается. Задачи, оставшиеся без обработки после сбоя worker-а, повторно забираются через 10 минут. Ошибки провайдера и базы повторяются с экспоненциальной задержкой от 30 секунд до одного часа. Одна синхронизация ограничена восемью минутами. При SIGINT или SIGTERM планирование останавливается, а текущая задача завершается до выхода.

Целевой интервал для адреса — пять минут, если провайдер и worker справляются с нагрузкой. При большой очереди или ограничениях провайдера фактический интервал увеличится. Глубина истории ограничена адаптерами: Bitcoin — до 20 страниц, каждый EVM-поток — до 10 страниц. Worker не отслеживает весь mempool, не атрибутирует личности, не хранит ключи и не подписывает транзакции. Паузы отдельного адреса пока нет: добавление адреса включает периодическое чтение настроенного публичного источника.

Очередь работает с доставкой «как минимум один раз». Повторные задачи безопасны благодаря уникальным ключам и upsert-операциям в базе. В Compose для Redis включено постоянное хранение; сохраняйте том Redis при перезапуске.
